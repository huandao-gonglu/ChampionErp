# ERP 与 New API 账号及计费接入调整方案

状态：账号交接、个人入口与会话/用户状态联动已开发，已完成专项回归。New API 源码位于同级独立仓库；已按用户确认在 `107.174.48.241` 完成内网部署与双用户验收，具体版本和实际验收见 [服务器部署记录](server-deployment.md)。正式 HTTPS 与官方收款不属于已验收结果。

## 1. 目标与职责

ERP 和 New API 部署在服务器上。用户从 ERP 注册、登录和使用 ERP，点击入口后进入已登录的 New API 页面，使用其原有的 Token 管理、充值与账单功能。

| 部分 | 负责内容 |
| --- | --- |
| ERP | 唯一账号与密码来源、注册/登录/改密/用户启停、ERP 会话、个人业务数据与桌面连接、New API 入口 |
| New API | 接受 ERP 登录身份、绑定本地计费用户、原生站点会话、模型 API Key、充值、余额、模型调用计费和账单 |
| 部署入口 | 两个服务的 HTTPS 转发与内部通信配置 |

账号身份以 ERP 用户 ID 为准，账务以 New API 为准。两个服务分别管理自己的数据，通过接口关联身份，不共同写用户表，不复制密码或密码哈希。ERP 不另建余额或扣费账本。

保留现有 Python、Vue、Electron、Pydantic AI、SQLite 和 `argon2-cffi` 账号实现。业务模型请求沿用现有 HTTP 客户端；账号控制面使用独立的短请求客户端，不创建个人业务空间或写入业务外部请求历史。不部署额外身份服务，不建设多身份源或通用 SSO 平台。New API 使用固定上游版本的改造分支，记录本次改动，便于升级时核对。

## 2. 沿用 ERP 账号与个人空间

1. 注册、登录、修改密码和管理用户继续调用 ERP 现有账号接口，不改为转交 New API 验证密码。
2. 继续使用 ERP 的密码哈希、HttpOnly Cookie 会话、CSRF 校验、角色权限和个人空间隔离。原业务用户 ID、数据目录与桌面归属保留。
3. 用户首次使用 New API 时，才根据成功验证的 ERP 身份绑定或创建本地计费用户，不在每次 ERP 注册时预先创建整套 New API 资源。
4. 身份绑定以稳定的 ERP 用户 ID 为唯一依据。New API 维护该 ID 到本地用户 ID 的唯一映射，不按相同邮箱自动合并账号。

New API 不接收 ERP 登录密码。自动创建的计费用户使用普通用户权限；ERP 管理员角色不自动变成 New API 管理员或 Root。运营管理账号单独明确绑定。

ERP 的日常登录和非 New API 业务不依赖 New API 在线。New API 不可用时，跳转、相应模型调用和账单服务返回明确错误，不改变 ERP 的账号来源。

## 3. 跳转到 New API

用户从已登录的 ERP 点击入口后自动进入对应 New API 页面，不再输入授权码、点击继续登录或确认账号。

1. ERP 入口经当前 Cookie、用户状态与 CSRF 校验，签发最多 60 秒的一次性票据。用户和会话只取自服务端，目标限定为 Key、钱包或消费。
2. 网页将票据作为表单 POST 提交到 New API 的固定入口；票据不进入 URL，绑定实际提交 Origin。
3. Electron 通过受限主进程 IPC 申请票据，打开只监听本机的临时页面，在系统浏览器自动 POST。临时入口一次性、60 秒有效，绑定当前桌面账号会话版本；不要求共享 Cookie。
4. New API 只接受固定 ERP 站点或本机 HTTP Origin，后端调用 ERP 固定内部接口验证服务身份、消费票据并确认会话。未知、缺失、`null` 或与签发不匹配的来源不能登录。
5. 按 ERP 用户 ID 解析既有计费用户，沿用原生会话和权限，再次检查关联 ERP 会话后以 303 跳转固定页面。ERP 管理员角色不会自动提升原生权限。

未登录直接访问 New API 时自动回到 ERP，已登录则继续交接。敏感操作仍保留重新验证 ERP 密码及原生操作 Proof，不把普通免登录扩展成跳过敏感认证。旧浏览器关联接口供已发布客户端和敏感验证使用，当前普通入口不再依赖它。

## 4. 关闭 New API 登录注册入口

New API 的登录/注册页面统一引导到 ERP，密码登录与公开注册接口在后端关闭。未登录用户直接访问充值、账单等页面时，也从 ERP 完成认证后返回目标页面。

本方案不调用 New API 的密码登录/公开注册接口，因此可以关闭其对应能力。可信 ERP 身份首次创建计费用户，走交接适配中的受控绑定逻辑，不能为了自动建用户重新开放公开注册。原生会话刷新、退出、账号状态校验继续保留。

源码改动集中在登录注册入口、身份绑定、登录交接和必要的会话联动。不重写原充值、账单与模型网关，不整体屏蔽 `/api`。具体开关和路由以固定版本核对结果为准。

## 5. 退出、改密与账号启停

- ERP 退出撤销当前 ERP 会话与桌面连接，并撤销该会话交接产生的 New API 站点会话；不连带退出其他设备。
- ERP 改密沿用原有全部会话失效规则，同时撤销该用户经 ERP 交接建立的 New API 站点会话。网页退出和改密不自动删除模型 API Key 或历史账单。
- ERP 禁用用户后禁止新的登录交接，并调用受控内部接口停用对应 New API 计费用户、撤销其站点会话；模型 API Key 的访问由 New API 的用户状态规则限制。重新启用恢复账号状态，不恢复已撤销的会话。
- 服务间调用部分失败时反馈尚未完成的步骤，可按既有用户/会话绑定重试，不能报告已全部完成。不为这些操作另建消息总线、通用事件同步平台或新的业务任务状态机。
- New API 页面主动退出只撤销其自身会话，保留 ERP 登录；用户从 ERP 再次进入时重新交接。退出不等于取消已提交的 ERP 业务任务。

## 6. 数据与计费边界

- ERP 商品、草稿、店铺授权、对话、素材、后台任务和桌面连接继续按用户隔离。现有 Store 和领域服务保留职责，账号接入不重写 Pydantic AI 执行机制。
- ERP 经 New API 调用模型时，使用当前用户所属的模型 API Key，由 New API 完成扣费与账单。登录令牌与模型 API Key 分别管理。
- 每个 New API 计费账号在创建或绑定时配发一把 `default` 分组的托管 Key。ERP 服务端按当前账号取用，文本模型 `dsflash`（`deepseek-flash`）和图片模型 `qwenflash`（`qwen-image-3.0`）共用这把 Key。ERP 设置页只读，密钥留在服务端，New API 按令牌所属用户检查额度和记录消费。
- 直接调用其他供应商、Browser AI 或 CLI 不会自动进入 New API 账单；本方案不增加事后补扣费流程。
- 充值、余额、支付订单和回调留在 New API，ERP 只提供入口。支付仍需满足官方直连要求，具体版本的渠道能力需在 New API 端核实，不因存在充值页面就认定满足。
- ERP 功能会员是否与 New API 订阅关联，后续另行定义。本次不将 API 配额套餐自动视为 ERP 会员。

## 7. 现有数据与部署

ERP 现有账号、密码哈希、用户 ID、个人空间、会话与业务记录继续使用，不迁移到 New API，不清理正在实施的账号功能。没有 New API 旧数据时，在首次有效交接中创建绑定。

如果目标 New API 已有用户、余额或账单，先备份并由运营人员核对、明确绑定已有账号；重复执行不得创建重复计费用户，不能以同邮箱静默合并余额或覆盖历史。原 ERP 数据初始化继续按上一份方案执行。

正式环境按阿里云 ECS 或腾讯云 CVM 部署两个独立服务，公开站点使用 HTTPS，内部服务通过受控接口通信。地址、证书、端口和回调以实际部署验收结果为准，同服务器不代表共用数据库、会话或 Cookie。

部署与备份沿用 [服务器部署记录](server-deployment.md)。备份同时覆盖 ERP 账号/业务空间及 New API 用户绑定、账务数据，并验证可恢复。本文说明集成职责与验收边界，实际已完成版本和部署范围以服务器记录为准。

## 8. 安全与维护职责

云厂商负责机房、物理设备、虚拟化平台等底层安全。操作系统和应用更新、HTTPS/安全组配置、账号权限、业务数据隔离、凭据保护和备份恢复仍由我们负责，云产品作为可复用工具使用。

本次安全工作限定为已有账号保护、两系统交接与权限、实际部署配置、备份和升级维护。保留现有 Argon2、会话撤销、CSRF 和隔离测试，不自研密码算法，不提前建设大型风控、跨设备调度或通用身份平台。

维护 New API 改造分支时保留版权与许可证声明，按 AGPL-3.0 的要求向网络使用者提供修改版对应源码的获取方式；升级时复测交接和账务相关入口。

## 9. 实施顺序与验收

1. 先完成并验收上一份 ERP 账号方案，确认已有账号、个人空间、网页和 Electron 登录稳定；不以本接入计划重做这些功能。
2. 固定 New API 版本和独立改造目录，检查原生用户创建、状态校验、会话签发/撤销与现有账务接口；列出需要修改的具体入口。
3. 完成 ERP 授权交接、New API 用户绑定和站点会话。验证两个用户从网页及 Electron 进入各自的 API Key、钱包与账单页面。
4. 关闭 New API 公开密码登录/注册，验证直接访问受保护页面可回到 ERP 登录，ERP 密码与注册流程仍正常。
5. 验证票据过期、重复消费、无效会话、目标页面和浏览器关联；用户 A 不能指定 B 的身份交接，普通用户不能因此成为 New API 管理员。
6. 验证退出、改密、禁用、启用及服务间调用失败后的实际结果。New API 不可用时，ERP 本地登录和非 New API 业务保持可用。
7. 用测试用户和测试模型验证按用户归属的 API Key、消耗与账单；实际收款需在官方支付渠道开通后单独联调，不用模拟回调代替收款验收。
8. 完成编译与架构检查、`.venv/bin/python -m pytest tests -q`、相关前端测试/类型/构建、桌面 Node 和安装包验证，以及固定 New API 版本的相关测试，再完成真实环境 HTTPS、回调和备份恢复验收。

复用现有业务测试，仅清理 New API 被替换的直接登录入口测试；保留 ERP 账号、密码及个人隔离测试。文档应记录开发回归与真实环境验收各自的结果，不把账号专项测试通过写成整套系统已经完成安全验收。
