# Agent 通用 Python 执行

主对话同时提供业务工具和可选的 `run_code`。简单查询、单项修改或参数已知的一次操作直接调用业务工具；需要循环、批量转换、计算、筛选大结果或组合依赖调用时，AI 才编写 Python。脚本使用同一套业务函数。执行层没有草稿、SKU、颜色或编码提取规则，也不要求新增每一种批量业务的工具。

## 装配与职责

- `erp_web/services/global_agent_chat_service.py` 在主对话的固定 Execution Profile 中声明 `python_tools=True`；其他 focused Agent 继续使用其专属工具。
- `erp_web/services/ai_agent_factory.py` 是唯一 Agent 装配入口；`erp_web/services/ai_code_mode.py` 只配置官方能力及边界适配。
- 已绑定的业务工具保留原生直接入口；其中无需审批、可同步完成的工具另外成为脚本函数。两种入口都经过 Pydantic ToolManager → `PydanticToolBridge` → `AiToolRuntime` → 原有业务函数，沿用参数校验、权限、所选对象范围、保存逻辑、取消检查和写回执。一次操作只选择一种入口，不重复执行。
- 发布、删除及持久 Job 留在脚本外，继续使用原生 Approval / Deferred。整对象 `draft_save`、`product_save` 仍为内部能力，不因 Python 被公开。
- `run_code` 的输入和结果使用原生消息及 Vercel 事件；嵌套调用保存在官方 `ToolReturnPart.metadata`，各次写入继续有数据库回执。脚本不承担事务，已完成写入不会因后续异常自动撤销。
- 官方脚本普通异常重试不包含完整嵌套回执，因此 `AgentRunStorage` 在下一次动态 instructions 中附加该失败脚本已保存的写回执摘要，防止成功操作被整段重放；不增加执行状态或新消息协议。
- 官方 Vercel Adapter 不展开 CodeMode 的嵌套 metadata。`/ui-messages` 因此在消息的 `metadata.business_write_receipts` 中附加实际落盘的脚本写回执，供现有表单按字段和版本更新；即使脚本后半段失败，已保存的前半段仍能显示。工具状态和流式事件仍全部由官方 Adapter 负责。

## 为什么直接使用 Pydantic AI 官方能力

已核对安装版本及 [CodeMode 官方文档](https://pydantic.dev/docs/ai/harness/code-mode/)，固定 `pydantic-ai-slim[openai]==2.44.0`、`pydantic-ai-harness[codemode]==0.34.0` 和 `pydantic-monty==0.0.23`。Harness 0.34.0 要求 Core 至少为 2.44.0，因此从 2.43.0 同步升级。

官方 CodeMode 已提供沙箱、Python 执行、工具函数声明、原生嵌套调度、REPL、重试和历史 metadata，无需自建 Python 编译器、脚本 RPC、Agent loop、审批或恢复协议。这里只使用 CodeMode 与 ToolOutputLimits，不接入完整 Coder、Shell、文件系统或上下文压缩能力。

薄适配的必要性：

1. Core 的整轮 UsageLimits 在模型响应边界检查，CodeMode 自带的嵌套调用上限只按单次脚本计算。`PythonToolBudget` 在官方工具执行 hook 中，以原生已完成计数加尚未结束的调用数，再调用原生 `UsageLimits.check_before_tool_call`。它不保存执行计划或另设额度；防止多段脚本及并发调用超过同一轮额度。若上游原生嵌套调度加入同样的预算预留，此适配应删除。
2. 官方 ToolOutputLimits 默认提供溢出文件读取工具。本项目只使用截断，因此按官方 Coder 的做法关闭该额外工具，不生成溢出文件。若上游支持直接关闭该工具，可移除子类。
3. Core 2.44.0 的 `Tool.from_schema` 不接收返回 Schema，因此 Bridge 使用原生 `Tool.prepare` 设置 `ToolDefinition.return_schema`，交由官方 CodeMode 生成返回类型。官方 Python 签名省略 `maximum`、`maxItems` 等约束，`ai_tool_contract_description.py` 从已有 Schema 机械生成约束说明，不实现类型编译器或另一套校验。上游签名能完整显示约束后删除这份补充说明。
4. Harness 0.34.0 的 `CodeMode(tools=...)` 会把选中工具转入脚本并移除其直接入口；官方支持按工具分流，但没有同一工具同时保留两种入口的选项，也没有明确禁止这种用法。`DirectAndPythonCodeMode` 使用公开 `get_wrapper_toolset` 扩展点，`DirectAndPythonToolset` 只在 `get_tools` 中合并原有工具和官方 CodeMode 工具。调用、重试、REPL、生命周期和嵌套调度全部继承官方实现，未重写 `call_tool`。上游提供保留直接入口选项时应删除这两个适配类。

两种入口并存有上下文成本：2026-09-25 对完整主对话工具集的隔离测量中，原来的 Python 入口方案为 8 个顶层工具，工具名称、说明和参数 Schema 的 JSON 共 52,338 字符；并存后为 60 个、99,283 字符。仅直接入口为 59 个、50,305 字符。这里是字符数，不是 token 或实际网络请求大小；不同模型的编码与缓存会影响真实费用和延迟。恢复直接调用减少了简单操作写脚本的必要性，但不保证总耗时下降。当前保留完整的参数、业务规则和 Python 返回类型说明，未通过删减校验契约来压缩上下文。

## 当前边界

- Python 由 Monty 沙箱执行，支持循环、条件、函数、正则、JSON、数学和 `asyncio.gather` 等；它是 Python 子集，不是可以任意安装依赖的 CPython。
- 不挂载宿主文件，不开放环境变量、数据库、Shell 或任意网络。业务数据通过已有工具函数读取；第三方包不可直接导入。
- 主对话总时限仍为 900 秒，整轮工具额度仍为 240，外层 `run_code` 与嵌套函数分别计数。沙箱纯计算最多 10 秒、内存 256 MiB、累计暂停点 4096；等待业务函数不消耗纯计算时限。
- 每段脚本最多发起 240 次业务调用，同时受整轮剩余额度约束。官方输出限制只裁剪脚本返回给模型的汇总，不裁剪脚本正在处理的数据及审计 metadata。
- `draft_attributes_read(scope=sku)` 默认返回当前目标的全部已选启用 SKU，不再设每页 50 条的固定上限；大量数据仍可用 `limit` / `next_offset` 分段。业务工具单次原始输出仍受 Runtime 的 256 KiB 上限约束，与脚本汇总长度、沙箱内存限制分别生效。
- 只读工具输出过大时，Bridge 通过原生 `ModelRetry` 提示缩小范围或分页；不扩大 Runtime 限额，也不自动决定业务参数。写工具的输出错误保留未知结果和实际回执，不因此触发重放。
- 变量只在同一个 Agent run 内共享，跨用户回合、后台暂停恢复或进程重启后重新建立，不自动重放脚本。

## 草稿成组保存

`draft_changes_apply` 是 ERP 的领域保存能力：脚本提供一份草稿的字段差异列表，每个 SKU 至多一项，公共属性用空 `sku_id`。单项可同时包含 `attributes`、`package_dimensions` 和 `stock`。编码提取、分组、单位换算等规则仍由 AI 写 Python 完成，运行时代码不包含颜色、编码或某种商品的规则。

- `draft_attributes_read` 返回读取版本 `updated_at`；SKU 明细使用具名字段 `DraftAttributeSku`，直接公开 `options` 等结构，不要求模型先探查字段名。
- 提交必须提供 `expected_updated_at`。网络校验前和获得商品锁后均检查版本、类目、SKU 所属/启用/选中状态和已发布限制；版本变化时整组不写，重新读取再计算。
- 一次提交共用类目定义；重复的枚举 ID/原文组合只核验一次。缓存仅在本次提交内有效，网络等待不持有商品锁。
- 所有变化在内存中通过后，只调用一次既有 `ProductStore.save_draft_content`。任何校验失败均不保存任何项；不承诺跨草稿、跨工具调用的事务。
- 回执包含本次各项实际已存值、变化键与统一的新版本。前端沿用现有写回执更新对应字段和版本，保留其他未提交编辑。
- `draft.write` 是成组工具基本权限，修改属性同时要求 `product.write`。所选草稿范围继续由现有门面约束。
- 单项属性工具仍服务于独立的公共/单 SKU 编辑，并保留网络校验期间按字段检查冲突的语义；成组工具要求整份草稿版本一致。两者共用纯属性合并规则和唯一 Store 保存入口，成组失败不会回退为逐条写入。

Pydantic AI 原生 CodeMode 负责脚本、工具调用与回执，不能自动把若干 ERP 保存调用合并成一次具备业务校验的草稿保存。因此此能力属于 ERP 领域层，并非自研 Agent 基础设施。没有增加编译器、RPC、执行计划、审批或等待状态机。

## 验证与性能含义

自动回归覆盖混合字段、198 个 SKU 单次落盘、同批枚举核验复用、失败不部分写入、版本冲突、取消、权限/所选草稿范围、发布限制、清空属性、重复提交无变化，以及前端同步结果和保存版本。受控模型测试用来验证工具连通和保存边界，不作为模型理解正确性的证据。

直接入口回归另外覆盖：不经过 `run_code` 的真实 Store 读取和单次保存、两种入口相同的参数校验及所选草稿限制、混合调用共用总额度、脚本之间插入直接调用后 REPL 变量仍可用，以及两种入口的独立写回执。

2026-09-25 使用当时配置的真实 `deepseek-flash` 做隔离简单查询：临时草稿有 1 个 SKU，用户要求查询数量。模型直接调用一次 `draft_read`，未调用 `run_code`；2 次模型请求、3.532 秒完成并回答正确，草稿内容未变化。完整生产工具定义保留，执行保护只允许读取临时草稿；未操作真实业务数据。这一条样本仅证明当前模型能选择直接入口，不能证明所有模型或所有任务都会选择正确路线。

此次恢复直接入口后的后端全量验证为 1836 项与 60 个子测试通过；相关模块编译、`pip check` 和 `git diff --check` 通过。隔离验收目录已清理，运行中的后端需重启加载新代码。

`scripts/eval_agent_python.py` 对颜色编码案例做真实模型验收：只读取得指定历史对话的完整初始 SKU 快照和平台定义，在临时数据库副本中走生产模型工厂、主 Agent、CodeMode 与 UI 入口。模型自行生成脚本，验收器仅在结束后评分，不把正确脚本交给模型。当前评分规则对应该案例，不能拿来评价任意用户任务；其他规则需增加对应评分器。

```bash
.venv/bin/python scripts/eval_agent_python.py \
  --conversation conversation_global_chat_122f90c6ebb34fd58d89156602e7c901 \
  --output /tmp/erp-python-evaluation.json
```

模型 API 使用当前 `global.chat` 配置，会产生正常模型费用；平台类目 API 使用历史定义替身，所有业务写入只发生在临时数据库，结束自动清理。报告记录脚本、调用数、时间、token、错误行及其他 SKU 字段是否被意外修改；未通过时返回非零退出码。报告可能包含案例业务文本，应放在临时目录，用完删除。验收耗时不包含真实平台 API，不能保证线上相同速度。
