# 微信 ClawBot 对话窗口

## 使用

1. 打开“系统设置 → 微信连接”，直接点击“扫码绑定”，窗口会显示取码进度及二维码。
2. 使用本人微信扫码并确认；如微信要求配对码，在窗口中填写。
3. 绑定成功后自动创建并绑定一段新的 ERP 普通对话，不要求事先创建或选择对话。
4. 在 ClawBot 中发送文字。网页打开 AI Work 中对应的对话，可以查看和继续同一段历史。

每次只绑定一个本人微信账号和一个普通对话。该会话新增的完整文字会按设置转发到微信，
包括从网页发起的回答；不补发绑定前的旧历史，不转发网页输入、推理正文和工具内部回执。
网页 `/new` 保持原有的新建对话流程，网页新建或切换对话不会改变微信绑定。
在微信发送独立的 `/new`，先新建普通 ERP 对话，再自动将微信绑定到该对话。
命令由消息入口直接处理，不调用模型；旧记录保留，旧会话已经提交的操作不会被自动取消，结果仍可在网页查看。
同一批消息中 `/new` 后面的输入进入新会话，重复投递同一命令不会重复建会话。
没有有效回复上下文时，新回复保留为待发送；先在微信向 Bot 发一条文字消息。

沿用 ERP 当前权限与审批模式；询问审批时，微信提示到 ERP 网页批准或拒绝。
第一版只支持文字。图片、语音、文件、群聊、多人使用和微信内审批不在范围内。
ERP 所在电脑和后端进程需要保持运行。连接通过主动访问 iLink 建立，不新增公网监听端口。
解绑清除渠道凭据和未投递队列，不删除 ERP 原生历史，也不撤销已提交的业务操作。

## 转发类型

“系统设置 → 微信连接”提供五类勾选项，默认全部开启，点击“保存转发设置”后生效。

| 类型 | 转发内容 |
| --- | --- |
| 回复与结果 | 普通回答、追问、要求补充信息和最终答复。原生协议没有这些内容的语义分类，因此合为一项，不根据文字猜测。 |
| 中途说明 | ERP 在执行过程中已完整生成的说明和阶段结果；不等待整轮结束，不逐字发送。 |
| 审批提示 | 提示前往 ERP 网页确认或拒绝，不在微信内执行审批。 |
| 失败或中断提示 | 运行失败、确认停止或输入无法处理的提示；不把中断当作已提交业务操作的撤销。 |
| /new 确认 | 确认已创建并绑定新对话；取消此项不影响 `/new` 本身。 |

中途说明只来自 ERP 已有正文，渠道不从工具日志总结进度，也不定时生成“正在处理”。
设置保存于 `app_config.system_settings.wechat_forward_types`，解绑和重启保留选择。
关闭某类会跳过该类待发消息，重新开启不补发；已经发出的网络请求无法撤回。
全部关闭后，微信文字仍交给同一个 ERP 对话处理，只关闭回复转发。

## 实现边界

- `wechatbot-sdk==0.3.0` 负责 iLink 协议；`wechat_channel_service.py` 只使用其通信接口。
  SDK 高层循环只在内存保存游标及回复上下文，不能提供 ERP 所需的持久接收确认。
  适配范围因此限定为登录状态展示、持久收件、会话映射和回复投递；不复制 Agent 循环、
  Deferred 协议或模型历史。将来 SDK 提供可持久化的收件确认与存储扩展点时，可替换这部分渠道适配。
- `chat_conversation_service.py` 提供网页和微信共用的输入接收、归属校验、取消及原生运行投递。
  Factory、Pydantic 原生消息、工具、审批和领域 Job 的职责保持一致。
  扫码确认与微信 `/new` 使用同一空会话创建入口：原生历史保存为空列表，可信归属预留在渠道库，
  不伪造用户消息、模型答复或运行记录。首次真实输入后继续使用原有轮次归属校验。
- 原生最终回答的 `metadata.chat_final` 与消息同次提交。中途正文复用 Pydantic AI 的
  `before_node_run`：在 `CallToolsNode` 前将当前 run 已完整生成、含工具调用的响应标记
  `metadata.chat_progress`，按既有 CAS 保存完整原生历史。不观察逐字片段，不另存模型消息。
  已核对安装的 Pydantic AI 2.44.0 与[官方 Hooks](https://ai.pydantic.dev/hooks/)；
  官方负责节点及消息生命周期，项目适配只负责历史提交和渠道文字投影。
  历史提交及运行结束后仅发送进程内唤醒通知，渠道随即读取历史、按类型进入持久投递队列；
  通知不携带正文，重启先扫描已提交历史与待发队列，网络发送失败只重试投递。
  渠道从已提交历史生成微信文字投影；
  仅隐藏开头的 `<think>` 块，未闭合的块不向微信发送，与网页的显示规则一致。
- `data/wechat-channel.sqlite3` 独立保存绑定、游标、回复上下文、收件和投递记录，文件权限为 0600。
  不修改 ERP 主库版本，不另存模型对话历史。已有投递表在事务内增加类型列并按原投递键回填，
  保留已有绑定、历史和待发消息。
  通信凭据不进入设置响应、模型或普通日志。
- 整批消息先与游标同事务落盘，再用稳定消息 ID 交给现有原生收件箱。渠道接收记录按账号和
  微信消息 ID 去重；ERP 接收成功后的崩溃不会导致同一输入再次执行。
- 回复观察位置和待发送内容同事务保存。发送失败只重试该回复，沿用原 `client_id`，不重新运行 ERP。
  iLink 对结果不明的请求不提供本项目已验证的恰好一次投递保证，因此网络响应丢失后可能看到重复回复。
- 后台线程随 AppContext 启停。未绑定时不发起微信网络请求；授权失效提示重新绑定。
  生产设计仍为单 ERP 进程，复用现有会话互斥，不增加第二个 Agent 执行进程。

官方参考：[SDK 项目](https://github.com/corespeed-io/wechatbot/tree/main/python)、
[腾讯 iLink 实现](https://github.com/Tencent/openclaw-weixin)。

## 验证

自动回归覆盖同一原生会话、网页投影、重复消息、接收中断、回复失败、重启恢复、身份过滤、
非文本提示、原生审批、登录重定向和配对码、空会话自动创建、`/new` 顺序及中断恢复，
以及扫码弹窗的加载、异步更新、完整遮罩手势和离开清理。
转发设置回归覆盖分类过滤、保存回显、全部关闭但继续执行、待发停发及不补发、旧队列迁移，
以及原生中途正文在最终答复产生前通过通知送达、不发送未完成片段。
自动测试使用隔离数据库和受控模型，不访问真实微信账号。
真实扫码、微信收发、断网重连与重启后的收发仍需本人完成验收，不能由自动回归代替。
