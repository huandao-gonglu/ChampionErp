ERP 是唯一账号与密码来源，New API 管理本地计费用户、模型 API Key、余额、消耗和账单。两者独立运行、各自持久化，通过接口关联用户，不共享账号数据库或密码哈希。

本次沿用 Python ERP 后端和正在实施的账号功能。New API 保留自身 Go 后端及前端工程，不将两套服务合并，也不建设额外身份平台。

## 2. 源码获取与版本固定

上游使用官方仓库 [QuantumNous/new-api](https://github.com/QuantumNous/new-api)。在实施开始时从[发布列表](https://github.com/QuantumNous/new-api/releases)选择并核对发布标签，记录完整提交 SHA；不把随时变化的 `main` 或镜像 `latest` 当作部署版本。

本地建议使用与 ERP 同级的 `/Users/hdgl/work/new-api`，作为独立 Git 仓库。实施前确认目录是否已存在；已有仓库继续使用并检查工作区，不覆盖现有文件。新目录的命令模板如下，标签需先替换为实际选择的版本：

```sh
NEWAPI_TAG='填写已选的官方发布标签'
NEWAPI_SOURCE_DIR='/Users/hdgl/work/new-api'
git clone --branch "$NEWAPI_TAG" https://github.com/QuantumNous/new-api.git "$NEWAPI_SOURCE_DIR"
git -C "$NEWAPI_SOURCE_DIR" switch -c codex/erp-integration
git -C "$NEWAPI_SOURCE_DIR" rev-parse HEAD
```

拉取后读取该版本适用的开发说明、许可证、Dockerfile、依赖锁文件和认证实现。Go、前端构建工具及依赖版本以该提交为准，不照搬旧教程的目录结构或登录协议。

在 New API 仓库内维护改造说明，记录上游标签及 SHA、改造提交、入口清单、数据库变更、构建方法和验证结果。源码、依赖和构建文件纳入版本控制；真实环境配置、商户密钥和业务数据库单独保存。

## 3. 功能保留与关闭清单

“关闭”同时约束页面入口和后端能力。仅隐藏按钮，仍允许直接请求原接口，不算完成。优先使用选定版本已有的功能设置；没有覆盖的接口在路由或业务入口明确禁止，不再增加一套用于切回旧登录方式的开关。

| 功能 | 处理要求 |
| --- | --- |
| New API 本地密码登录、公开注册 | 关闭后端能力；原页面引导至 ERP |
| New API 密码找回、重置和修改密码 | 关闭本地处理，账号操作回到 ERP；不能留下找回密码后独立登录的路径 |
| 第三方 OAuth/OIDC、微信、Telegram、Passkey 等独立登录与绑定 | 关闭本次不使用的认证和绑定入口，避免绕过 ERP；本项目的 ERP 交接入口单独保留 |
| New API 本地账号身份修改、注销 | 关闭与 ERP 身份管理冲突的字段写入及注销入口；语言、展示偏好、账务设置等独立字段可保留 |
| 站点会话刷新、退出、状态校验 | 保留原生实现，接入 ERP 会话撤销联动 |
| 模型 API Key 创建、查看、编辑和撤销 | 保留原生权限与用户归属校验；与站点登录令牌分开管理 |
| 钱包、余额、充值记录、消耗明细及账单 | 保留原有页面和账务逻辑 |
| 支付下单及回调 | 仅启用实际接入的官方支付渠道；具体要求见第 5 节 |
| 模型网关、渠道选择、价格、额度检查与扣费 | 保留；ERP 使用各用户自己的模型 API Key 调用 |
| New API 原生配额订阅 | 保留能力，不自动变成 ERP 功能会员；是否开放购买随实际计费方案配置 |
| 运营控制台 | 保留渠道、价格、账务、用户状态和必要设置；普通用户不得访问 |
| 签到、推广返佣、站内聊天等其他产品入口 | 首版不开放，通过已有模块设置关闭；确有相关后端写入能力的，同时关闭。无需为裁剪导航大规模删除无关底层代码 |

普通用户首版主要入口为模型 API Key、钱包充值、消耗账单和退出。保留必要的服务说明、隐私信息及源码获取入口；不把 ERP 开发约束展示为产品文案。

关闭身份修改时，要检查通用个人资料接口和运营用户管理接口，限制其创建独立账号、修改密码或改变 ERP 身份绑定的能力；允许运营者继续管理 New API 的额度、分组及账务状态。身份字段与账务字段分别处理，不能通过删除整个用户模块破坏计费。

### 3.1 需要核对的后端入口

本轮核对了官方主线的[路由文件](https://github.com/QuantumNous/new-api/blob/706144769e5bed5a47b78721e3bb11da3cf4c0b9/router/api-router.go)，以下用于定位，最终路由清单必须在锁定版本补齐：

- 登录注册：`/api/user/login`、`/api/user/register`，以及登录验证、Passkey 等分支。
- 密码找回：`/api/reset_password`、`/api/user/reset`，以及个人资料接口中的密码更新字段。
- 外部身份：`/api/oauth/*` 及用户侧身份绑定、解绑入口。
- 个人资料：`/api/user/self` 的身份更新、注销，与仍需保留的查询能力分别处理。
- 必须保留：`/api/user/auth/refresh`、`/api/user/auth/logout` 及相关会话管理；支付回调、模型 Key 与账务接口单独核对。

不能整体封禁 `/api/user/*` 或 `/api/*`，这些路径同时承载会话与账务能力。路由清单应记录请求方法、处理方式和实际验证结果，而不是只列页面地址。

## 4. 源码修改边界

### 4.1 身份绑定与会话

New API 增加 ERP 身份绑定记录，以稳定的 ERP 用户 ID 唯一关联本地计费用户 ID；由数据库唯一约束保证重复或并发交接不会产生重复计费用户。不按邮箱、昵称或页面提交的用户 ID 自动认领已有账号。

首次有效交接创建普通计费用户，复用 New API 的用户初始化及额度规则，不复制 ERP 密码。ERP 未验证的邮箱不能在 New API 中标记为已验证；本地用户模型如有必填字段，按其约束适配，不给用户生成可独立登录的默认密码。

普通入口采用来源绑定的一次性票据自动交接。ERP 当前会话经 CSRF 校验签发最多 60 秒票据，网页或桌面本机桥接页面以表单 POST 交给 New API；New API 校验实际 Origin，再由后端访问 ERP 固定交换接口消费票据。跳转目标使用钱包、账单、Key 等固定枚举，不接受任意返回地址。

New API 复用锁定版本的原生会话签发及前端登录初始化流程。若该版本使用 Access Token 和 Refresh Cookie，回调后通过原生刷新恢复前端身份，不把 Access Token 放入跳转 URL 或另建长期登录令牌。实现前核对[官方认证说明](https://github.com/QuantumNous/new-api/blob/706144769e5bed5a47b78721e3bb11da3cf4c0b9/docs/authentication.md)。

记录 ERP 会话关联标识与交接产生的 New API 会话标识，用于按原集成方案撤销；不得把 ERP 的可用会话凭据复制进绑定表。服务间撤销、启停接口只接受可信服务调用，普通用户不能指定其他用户或会话。

只修改交接适配、绑定持久化、必要会话联动和页面入口。原生会话校验、额度检查、支付订单及扣费链路继续使用原实现。遇到敏感操作必须二次认证的版本，核对其原生验证要求；必要时由 ERP 完成重新认证，再兑换有用途约束的短时验证结果，不能为免登录删除原有安全校验。

### 4.2 运营账号初始化

先完成 ERP 管理员初始化，再在 New API 仅内网可访问的阶段完成原生安装初始化。提供服务器本地的受控绑定命令，将明确指定的 ERP 用户绑定到 New API 运营账号，记录绑定结果；重复执行不得重复建用户或扩大权限。

该绑定独立于 ERP 的管理员角色，不提供普通用户可调用的提权接口。完成运营登录验证后，再开放公共站点；不为运营者保留可绕过 ERP 的公网密码登录入口。已有用户、余额和账单的环境先备份、核对绑定，不重建用户库。

### 4.3 ERP 侧配套改动

ERP 提供登录交接与账号状态联动。首次创建或绑定 New API 账号时，New API 在同一事务内为该用户配发一把随机的 `default` 分组托管 Key。已有绑定在登录交接或首次模型调用时补齐。ERP 通过内部服务接口按当前账号取用，前端只展示两款固定模型。用户在 New API 中另外创建的普通 Key 仍由本人管理。

Electron 与系统浏览器的交接使用本次 ERP 集成实现的可信入口，必须实际验证两者不共享 Cookie 时仍能完成交接；不能以开发浏览器已登录 ERP 作为桌面免登录验收结果。ERP 账号、个人空间和 Pydantic AI 执行机制不在本次重写。

## 5. 支付接入边界

用户要求直接接入支付宝、微信支付等官方服务。New API 中存在充值页面、支付宝展示项或第三方支付适配器，不足以证明已满足官方直连要求；当前未确认所选发布版本具备所需的官方直连实现。

实施时核对具体渠道的下单地址、SDK/协议、商户签约要求、回调验签、订单查询与入账幂等。满足条件的原生能力直接复用；若缺少所选官方渠道，在 New API 内补充该渠道适配并复用其订单、余额和账单能力。ERP 不新增支付订单库或收款回调。

Stripe、Creem、易支付等不符合本次官方直连选择的渠道不启用，也不作为自动替代方案。商户资质和官方渠道尚未就绪时，可以完成账号、Key 和模型计费验收，但充值入口应保持不可下单，并明确记录实际收款尚未验收。

支付能力的具体开发以选定渠道核对结果为准，不在源码拉取阶段同时建设多渠道收银台、ERP 会员或财务平台。正式联调使用官方测试环境或另行确认的实际支付安排，不以模拟通知代替真实收款验收。

## 6. 修改版构建与交付

使用锁定提交的[官方 Dockerfile](https://github.com/QuantumNous/new-api/blob/706144769e5bed5a47b78721e3bb11da3cf4c0b9/Dockerfile)作为构建起点，构建改造后的完整前后端。服务端使用与目标服务器相符的 CPU 架构；在 Mac 构建时显式核对目标平台，避免把仅适用于本机的镜像发布到服务器。

以改造提交 SHA 标记镜像，例如 `champion/new-api:<改造提交SHA>`；发布记录同时保存镜像摘要、上游 SHA、改造 SHA 和所需配置。部署使用这个已验证的修改版镜像，不能改完源码后仍拉取官方 `latest` 镜像。

源码仓库内交付部署模板、无真实密钥的配置示例、入口清单和改造说明。构建产物通过镜像仓库或镜像归档交付；运行数据库及密钥不打进镜像。

保留 New API 的版权、许可证及第三方声明，并按其 [AGPL-3.0 许可证](https://github.com/QuantumNous/new-api/blob/706144769e5bed5a47b78721e3bb11da3cf4c0b9/LICENSE)向网络使用者提供该修改版对应源码的获取方式。提供的源码应与实际运行提交一致，排除真实业务数据与部署凭据。

## 7. 服务器部署

### 7.1 服务与数据

正式目标为阿里云 ECS 或腾讯云 CVM，具体服务器和公网地址待实际部署确定。现有服务器情况见 [服务器部署记录](server-deployment.md)，本文不把临时环境视为已经完成正式切换。

首版采用单实例 New API、独立持久化目录，使用锁定版本支持的 SQLite；不因接入 New API 迁移 ERP 数据库。源码已支持的单机能力优先复用，不额外引入 Redis、集群或共享数据库。若所选版本确有依赖变化，实施记录中说明依据及对应调整。

建议目录：部署文件位于 `/opt/new-api/deploy`，运行配置位于 `/etc/new-api/runtime.env`，持久化数据位于 `/var/lib/new-api`。目录权限限定给实际运行服务及运维账号，按镜像运行身份设置写权限，不使用全局可写权限解决启动问题。

下面是部署模板的最小结构，实际文件应随源码交付；`NEWAPI_IMAGE` 在 Compose 的部署环境中填写已验证的镜像版本，`runtime.env` 保存运行配置：

```yaml
services:
  new-api:
    image: ${NEWAPI_IMAGE:?请设置已验证的修改版镜像}
    restart: unless-stopped
    ports:
      - "127.0.0.1:3000:3000"
    volumes:
      - /var/lib/new-api:/data
    env_file:
      - /etc/new-api/runtime.env
    environment:
      PORT: "3000"
      TZ: Asia/Shanghai
      DEFAULT_LANGUAGE: zh-CN
      SQLITE_PATH: /data/new-api.db
```

配置项在锁定版本核实。当前官方[环境配置示例](https://github.com/QuantumNous/new-api/blob/706144769e5bed5a47b78721e3bb11da3cf4c0b9/.env.example)包含 SQLite 路径及会话相关设置。不要原样复制[官方 Compose 示例](https://github.com/QuantumNous/new-api/blob/706144769e5bed5a47b78721e3bb11da3cf4c0b9/docker-compose.yml)中的默认密码、公开端口、`latest` 镜像或与本次无关的数据库服务。

运行配置至少包括 New API 原生会话密钥、ERP 固定交换地址、服务间凭据及公开站点地址。生产启用安全 Cookie 和实际 HTTPS Origin 校验，准确配置可信反向代理；具体变量以锁定版本为准。实际密钥在服务器生成，配置文件限制读取权限，不写入仓库、前端包或日志。

### 7.2 公网入口

反向代理统一处理 HTTPS，分别转发 ERP 与 New API；后端业务端口不直接暴露公网，普通电脑通过正式 HTTPS 地址访问，无需配置 SSH 通道。

优先使用各自独立的主机名和根路径。尚无域名时，需要先确定证书可验证的访问地址及端口；如果使用服务器 IP，证书必须覆盖该 IP，不能通过忽略证书错误交付。相同主机名或 IP 的不同端口仍共享 Cookie 的主机范围，需要检查双方 Cookie 名称和作用路径，不能仅凭端口判断隔离。

不默认把 New API 挂在 `/newapi` 子路径下。若实际选择该形式，需要验证前端资源、API 根路径、Cookie、刷新页面及支付返回地址均支持，避免与 ERP 的 `/api` 冲突。公开地址确定后同步配置 ERP 入口、New API 返回地址与官方支付通知地址。

票据交换及用户/会话联动通过服务器本机或受控内网连接。公网模型 API 继续使用 New API 原生模型 Key 鉴权；官方支付异步通知保留独立可达路径和验签，不要求支付平台先登录 ERP，也不因关闭登录注册误封支付通知。

上线前先完成仅内网可访问的初始化及运营账号绑定，再配置代理和站点访问。云厂商负责底层设施，我们负责系统与应用更新、配置、账号权限、数据备份及实际恢复。

## 8. 数据备份与升级

New API 数据单独备份，覆盖身份绑定、会话关联、用户、模型 Key、余额、订单和消耗账单；ERP 账号及个人业务空间仍按原部署方案备份。配置和密钥通过受控方式备份，不能只保存镜像或源码作为业务恢复材料。

SQLite 使用一致性备份；运行中不能只复制主数据库文件而忽略尚未合并的 WAL。若锁定版本另设日志数据库或数据文件，一并纳入实际清单。至少验证一次恢复后用户绑定、余额与账单一致，历史 ID 不变。

升级先固定新的上游提交，在改造分支合并并核对入口清单，完成测试后生成新镜像；切换前备份实际数据。没有数据结构变化时可切回旧镜像；存在迁移时先核对旧版本能否读取，必要时按备份恢复，不能把切回镜像视为自动回滚数据库。

升级不重新创建计费用户、不按邮箱重新绑定，不因新版本增加登录方式而自动开放新的认证入口。保留原始用户与账务数据的读取、迁移能力。

## 9. 实施顺序与验收

1. 完成并验收原 ERP 账号任务；固定 New API 上游标签、SHA，建立独立仓库和改造分支。
2. 核对锁定版本的路由、原生会话、敏感操作验证、运营初始化和支付渠道，补齐具体改动清单。
3. 完成身份绑定、交接及会话联动，关闭第 3 节所列独立身份入口；保留原生账务与网关。
4. 运行 New API 仓库规定的相关后端、前端测试及构建检查，再构建目标架构的修改版镜像。ERP 改动按项目要求完成编译、架构测试、全后端测试，以及相关前端和桌面检查。
5. 在目标环境完成内部部署、运营绑定、HTTPS 配置、两个普通用户验证和备份恢复；满足支付接入条件后单独完成官方渠道联调。
6. 更新两仓库实施记录与服务器部署记录，区分代码已实现、测试已通过、环境已部署和真实收款已验收。

必要验收场景如下：

| 场景 | 通过标准 |
| --- | --- |
| 两个用户分别从 ERP 网页及 Electron 进入 | 身份正确；各自只能操作自己的模型 Key、钱包和账单；浏览器交接关联实际生效 |
| 未登录直接打开 New API 账务页面 | 进入 ERP 认证流程，完成后返回固定目标页面，无任意跳转 |
| 直接请求原登录、注册、找回密码及外部登录接口 | 后端确实拒绝，通用资料接口不能绕过限制修改身份 |
| 票据过期、重放、替换用户或服务凭据无效 | 拒绝交接，不创建错误用户，不提升权限 |
| 首次交接重复或并发发生 | 同一 ERP 用户仅对应一个计费用户，已有余额及账单不被覆盖 |
| ERP 退出、改密、禁用与启用 | 按集成方案的会话范围生效；调用失败说明未完成步骤，可按已有绑定重试 |
| New API 单独退出或暂时不可用 | 单独退出不撤销 ERP 会话；故障不阻断 ERP 登录和其他业务 |
| 用户管理模型 Key 并经网关调用 | 必要认证可完成，扣费归属正确；直接调用其他供应商不写入 New API 账单 |
| HTTPS、代理与服务重启 | 真实地址可用，会话刷新正常，业务端口未公网直连，数据与绑定保留 |
| 官方支付及备份恢复 | 支付按真实结果验收；备份恢复后用户、绑定、余额与账单一致 |

测试清理仅针对被替换入口的旧成功路径及废弃实现，保留或改写为“接口已关闭”的回归验证。保留原生会话、权限、支付验签、扣费和账务测试，也保留 ERP 账号及个人空间测试；不能为通过测试删除仍有效的业务约束。

## 本次实现与验证补充

- ERP 网页的「个人账号」增加「Token 与账单」。点击后自动签发 60 秒、来源绑定且只能消费一次的票据，经 POST 直接进入 New API；普通登录不再要求手动输入或确认关联码。敏感操作重新验证 ERP 密码，同账号可在不同 ERP 设备完成验证，原登录关联仍须有效；已有 MFA 不降级。
- 退出、改密和启停先完成 ERP 状态变更，账号库在同一事务写入待同步记录。New API 不可用时返回 `newapi_sync_pending` 并展示提示，每 30 秒按顺序重试，不阻断 ERP 登录与业务。
- New API 首次交接只创建普通计费用户；运营账号由服务器命令显式初始化或绑定，普通用户与 ERP 管理员角色都不能自动提权。独立账号、身份修改、站内聊天、签到与推广转移均有后端限制。模型 Key、钱包、账单、原生权限和会话机制保留。
- 在线收款下单关闭，保留余额和历史。当前未接入官方支付宝/微信商户，也未用聚合支付替代，不以测试充值或模拟通知宣称实际收款通过。
- 真实 SQLite 3.50.4、MySQL 8.4.13、PostgreSQL 18.6 已验证交接与撤销；三种数据库的新库和固定官方镜像旧库升级均连续启动两次，已有用户、Key、余额、日志、会话与索引保持一致。迁移工具只操作独立测试库。
- ERP 全后端、前端、桌面以及 New API 账号相关 Go/前端回归的最终结果记录在服务器文档。全量 Go 的一个代理错误断言在未修改上游中也会失败，已单独记录，不能表述为全仓全部通过。
- 内网入口使用 ERP 的 `127.0.0.1` 与 New API 的 `localhost`，通过 SSH 转发；端口不同不能隔离 Cookie。正式环境仍应使用两个独立 HTTPS 主机名，不能把此次内网部署当作正式云环境切换。
