# 跨境巴士履约 V1

本阶段在现有授权配置、订单中心和订单详情中完成履约，不新增首次接入流程或独立日志页面。

## 产品入口

- 授权配置 → 跨境巴士 → 账号授权：企业 `client_secret` 获取/刷新 Token；跨境巴士账号密码换取用户授权记录 `app_uid`。密码只用于当次请求，不落库，密钥与 Token 不返回前端。
- 同模块 → 默认履约：从已同步订单选择实际平台配送来源；配置渠道、仓库、必选/可选服务和人工确认的兼容仓库。
- 订单中心 → 详情 → 跨境履约：查看详情、录入/管理包裹、获取/更新面单、报单前覆盖方案、立即提交、状态同步、取消和异常详情。列表只保留“详情”入口，分别展示平台状态和 ERP 处理进度；采购登记、国内单号、面单、预报等事实在详情中核对。

默认方案按平台、授权店铺、履约模型、平台仓库、配送方式和目的国精确匹配。
不会从俄罗斯或渠道名称猜测 CEL、UNI、GUOO，不会自动比价或替换平台指定配送方式。
订单中没有真实配送来源时暂停预报；平台仓履约订单不进入此链路。

## 展示边界

- 平台状态按统一状态显示；Yandex 备货、打包、已备妥作为平台附注，不与采购登记、跨境仓进度混用。
- ERP 处理进度使用实际采购数量及本地仓库回执：待采购登记 / 采购登记中 → 待预报 → 已创建预报 → 待到仓 / 包裹已入库 / 已打包 → 仓库已发货。取消、未知创建结果和错误单独提示；错误不覆盖最近确认的仓库进度。
- 国内单号和国际面单可分别补齐，没有单号只显示“未录入”，不推测供应商未发货；已录入单号不等于已到仓，已保存面单不等于已发货。
- 仓库已发货是 V1 的终点。页面不展示尚未接通的国际运输、妥投、签收或履约“已完成”。平台已发货但没有跨境预报时明确显示“无跨境预报”，不能认定这条 ERP 履约链路已经完成。
- 列表批量读取脱敏履约摘要，不创建履约记录，也不发起远端请求；详情与列表共用进度展示规则。

## 首条链路

1. 完成平台授权，并在订单中心同步待发货订单。
2. 在现有授权模块授权跨境巴士，读取真实合作渠道、仓库和服务，确认承接关系并保存默认方案。
3. 在“商品与采购”确认来源并登记实际采购记录。
4. 获取平台生成的国际面单及对应面单号，并录入国内包裹。目的国未由平台提供时人工填写 ISO 两位代码；已有目的国不可覆盖。
5. Yandex 单箱待发货订单支持“获取平台面单”；默认自动预报开启且方案、包裹齐备时后台自动获取。读取平台 PDF 和箱号后托管，成功后保存对应面单资料。其他平台或平台不提供箱号时，可人工粘贴公开 HTTPS 地址或上传不超过 8 MB 的 PDF。上传复用现有默认 S3 托管，在独立对象路径保存，并以匿名下载校验内容一致；不使用本机地址作为仓库面单地址。
6. 包裹逐项关联有效采购记录，填写快递公司、单号和数量。提交前必须覆盖全部订单商品；累计包裹数量不能超过采购或订单数量。
7. 默认自动预报开启时资料齐备后自动创建正式预报；关闭时点击“立即提交”。创建会使用合作仓库的真实必选服务，不假设服务编号。
8. 后台查询仓库状态和包裹入库状态，直到跨境巴士已发货 → ERP **履约状态**已发货。平台订单状态仍由平台订单同步负责。

本版先补齐资料再创建正式单，避免将缺少面单或商品数量的正式单送入仓库。创建后仍可更新面单和完整国内包裹列表，打包后锁定资料。
面单读取不自动修改平台分箱、不改变平台发货状态。Yandex 需具备订单处理权限，且已在平台生成单箱面单；多箱订单不能把多张面单压成一个箱号，暂停自动获取并要求人工处理。Market Yandex Go 不支持箱号数据接口时使用人工补充。当前 Ozon、Mercado Libre 尚未接入自动获取，页面明确显示人工补充提示。

Yandex 官方接口：[订单面单 PDF](https://yandex.ru/dev/market/partner-api/doc/ru/reference/order-labels/generateOrderLabels)、[箱号数据](https://yandex.ru/dev/market/partner-api/doc/ru/reference/order-labels/getOrderLabelsData)。直接调用固定面单路径，不依赖即将退役的回执 `url` 字段；采用平台返回的 `fulfilmentId` 箱条码，不把 `orderNum` 当面单号。

获取失败保存独立 `label_error`，在面单区域显示原因；自动获取按 5 分钟间隔重试，人工按钮可以立即重试。重新获取失败保留原面单，不覆盖仓库状态错误。获取与预报共用占位；重复点击、期间取消、资料版本变化及授权切换均不得写入过期结果。

S3 上传前 `HeadObject` 返回 404 表示对象尚不存在；SDK 保留原始回执，统一请求管理不为它创建拒绝记录或增加连续失败计数。上传与对象校验、公开读取使用同一操作范围，正常的不存在查询不能阻止上传后再次校验。其它请求的 404、S3 的 403 等仍按错误处理。交付错误明确显示托管配置、S3 上传/对象校验或公开下载阶段，并保留已脱敏的权限、DNS、网络原因。

## 协议和状态

官方文档：[跨境巴士 API](https://kuajing84.apifox.cn/)。服务端只使用官方生产域名 `https://api.service.kuajing84.com`。

合作仓库实际回执中的 `section_id` 和仓库 `id` 可能是字符串，服务费用 `gold` 也可能是字符串。
在协议边界统一转换为数字，再供默认方案、仓库选择及后端承接校验使用；已保存的合作仓库缓存读取时做相同归一化。
页面直接展示已读取的合作仓库，不以默认方案数量或平台订单配送来源数量判断合作仓库是否为空。

| 行为 | 官方接口 |
| --- | --- |
| 企业 Token | `/erpapi/token/index`、`/erpapi/token/refresh` |
| 用户授权/核验 | `/erpapi/user/authorization`、`/erpapi/user/queryauthorization` |
| 合作仓库与服务 | `/erpapi/storehouse/cooperationStorehouse`、`/erpapi/storehouse/searchStorehouseSection` |
| 正式预报 | `/erpapi/order/createOrder` |
| 国际面单 | `/erpapi/order/updateOrderSheet` |
| 完整包裹替换 | `/erpapi/order/updateOrderPackage` |
| 取消 | `/erpapi/order/cancelOrder` |
| 状态、创建核实和入库核实 | `/erpapi/orderlist/status`、`/erpapi/orderlist/search` |

| 确认事实 | ERP 履约状态 |
| --- | --- |
| 尚未预报 | `NEW` |
| 获得唯一远端订单 ID | `FULFILLMENT_CREATED` |
| 正式单待打包，尚无全部入库证据 | `WAITING_DOMESTIC_SHIPMENT` |
| 查询列表的全部包裹 `status=1` | `WAREHOUSE_RECEIVED` |
| `order_status=1` 已打包 | `PACKING`（界面“已打包”） |
| `order_status=3` 已发货 | `SHIPPED` |
| 问题件 | `EXCEPTION` |
| 仓库确认已删除/取消 | `CANCELLED` |

官方状态接口不提供入库状态，不能把待打包直接认定为已入库。未知状态或查询失败保留最近确认进度并显示错误。`COMPLETED` 保留为内部状态，本阶段不自动推进到签收完成。

## 并发、核实和取消

- `(platform, account_id, platform_order_id)` 在 SQLite 中唯一，使用稳定的 ERP 预报号；原有平台订单身份保持不变。
- 写请求不隐式重试。创建前原子占位，写前标记结果未知；超时或进程退出后只查询核实，不能再创建一张单。
- 查询接口按预报号前缀检索，必须读完分页并精确匹配 `sheet_info.section_order`；还要核对渠道和仓库，不能拿第一条结果当本单。
- 查询不到不等于未创建，仍保留“创建待确认”；需要人工联系跨境巴士核实，不能点击普通重新提交绕过。
- 所有人工修改携带 `revision`。版本冲突不覆盖新数据；包裹弹窗保留输入，刷新版本后要求人工复核。
- 修改本单方案时暂停自动预报，编辑租约 5 分钟，打开的弹窗每分钟续期。保存/取消恢复预报，关闭浏览器后租约会失效。
- 平台取消和人工取消都优先停止创建；若创建可能已经发送，先核实创建结果再取消远端单。
- 取消发送前持久化占位，超时后只核实，不自动再次取消。收到成功请求回执也要等待仓库查询确认。
- 仓库已发货时保留已发货，并持续显示取消冲突。已入库包裹需人工与仓库处理。
- 账号切换后禁止对旧授权下的履约单继续写入。
- 所有远端请求复用统一外部请求管理；资料更新或授权请求结果未知时，需先按现有请求管理流程核实和解除阻断，不绕过管理器重放。

## 开发入口

- `schemas/fulfillment.py`：配送、配置、面单、包裹、命令和详情契约。
- `stores/fulfillment_store.py`：与订单库共用 SQLite，保存配置、账号凭据、规则、操作占位和履约事实。
- `services/crossborderbus_client.py`：官方协议、Token 刷新、授权、查询分页和安全错误映射。
- `services/fulfillment_service.py`：确定性履约编排、校验、后台恢复和状态同步。
- `services/platform_label_service.py`：复用现有店铺授权读取平台 PDF 与箱条码，核对订单及单箱约束。
- `services/fulfillment_label_service.py`：PDF 交付和公开内容核验，复用唯一 S3 SDK 边界。
- `facades/fulfillment_facade.py`：按当前平台账号范围装配；`AppContext` 持有服务并负责关闭。
- `http_route_units/fulfillment_routes.py`：薄 HTTP 适配；全部写请求经过公开请求契约校验。

GET：`/api/crossborderbus/settings`、`/api/crossborderbus/services`、`/api/orders/fulfillment`。
POST：`/api/crossborderbus/{authorize,catalog,save-rule,delete-rule}`；`/api/orders/fulfillment/{fetch-label,upload-label,label,parcels,plan,pause,resume,submit,sync,retry,cancel}`。
这些接口在能力治理清单中登记为可信界面入口，不向模型开放代报、代采购或代取消，不新增 Agent 生命周期。

## 验证边界

后端使用隔离 SQLite 和模拟远端回执测试幂等、重启核实、完整数量、兼容范围、账号隔离、入库/打包/发货和取消冲突；前端用组件测试验证实际表单操作、版本冲突、仓库服务切换和遮罩手势。

真实跨境巴士授权、合作仓是否承接具体平台配送方式、资金扣费和生产仓发货仍需用真实账号及测试订单验收；不能把模拟回执测试视为生产履约已完成。
