你是一名资深的产品设计师、交互设计师和后台系统 UI 设计师。请按照以下统一规则，设计或重新设计我提供的页面。

这些规则适用于不同业务页面。具体布局应根据页面的核心对象、任务和操作频率决定，不要把所有页面套成同一种结构。

## 一、整体设计方向

采用紧凑、清晰、克制的桌面工具型产品风格：

- 中性深灰背景，绿色作为主题高亮色。
- 小圆角、细边框、轻量分隔、紧凑控件。
- 强调信息密度、操作效率和长时间使用的舒适性。
- 通过对齐、间距、字号、字重和少量背景层次建立信息层级。
- 避免大面积纯黑、厚重阴影、渐变、霓虹发光、玻璃效果和装饰性元素。
- 不要把后台页面设计成宣传落地页，不使用巨型标题、巨大按钮和大量无效留白。
二、亮色与暗色双主题配色规范

1. 主题总原则

页面必须支持亮色和暗色两套主题，强调色统一采用绿色。

亮主题：白色主区域、浅灰侧栏、浅灰表头、细灰边框、深灰文字。

暗主题：中性深灰背景、浅一级深灰面板、细灰边框、浅色文字。

两套主题共享相同的布局、字号、间距、圆角、控件尺寸和交互规则。

主题切换只调整颜色及必要的对比度，不改变页面结构和操作位置。

未指定主题时，跟随应用当前主题设置，不由各页面自行决定。

使用统一的语义化主题变量，不在不同组件中随意硬编码颜色。

原规范中仅针对“深灰＋绿色”的整体描述，统一更新为“亮暗双主题＋绿色强调”。

使用规则：

亮主题中的绿色文字使用深绿，保证在白底上的辨识度。

亮主题的选中行、选中卡片使用淡绿底色，正文仍使用深色文字。

暗主题的选中区域使用低亮度深绿底色，正文仍使用浅色文字。

复选框、启用开关、选中指示线使用清晰的绿色，并保证内部标记可辨认。

普通悬停优先使用中性灰；只有需要表达选中、焦点或明确强调时才使用绿色。

普通次要操作使用中性色按钮，不把所有按钮、图标和链接都染成绿色。

警告和失败可以使用少量琥珀色、红色，但必须配合文字或图标说明。

4. 亮主题的具体呈现方式

页面与面板

主工作区以白色为主，侧栏和必要的辅助区域使用浅灰。通过对齐、留白和细分隔线组织内容，避免给每个模块都套一层灰底卡片。

输入框与按钮

普通输入框使用白底和细灰边框；普通按钮使用白色或浅灰背景。焦点状态用绿色边线表达，不依靠大面积阴影或发光。

表格与列表

表头使用浅灰底，数据行使用白底，行间使用细灰分隔线。悬停为浅灰，选中为淡绿，文字保持清晰。

导航与页签

普通导航项使用深灰文字。当前项通过绿色指示线、深绿文字或轻微淡绿底色表达，不使用大面积高饱和绿色铺满导航区域。

图片与图表

商品图片、品牌标识等内容保留自身颜色。图表的主要数据系列使用绿色；多系列图表可以使用清楚可区分的辅助色，不将参考图中的青蓝色作为应用主强调色。

5. 双主题一致性要求

不通过简单颜色反转生成亮主题。

不因切换亮主题而增加圆角、阴影、装饰或留白。

不因切换暗主题而把所有背景统一改成纯黑。

正文、辅助文字、边框、悬停、选中、焦点和禁用状态都应有对应的主题变量。

不仅依靠颜色表达状态，继续保留必要文字、图标和选择标记。

同一功能在两个主题中的位置、层级和操作方式必须一致。

本节只补充主题与配色。既有硬性规则继续适用：全局保存、提交等操作固定在页面右上角；禁止业务弹出窗体；详情使用右侧页内分栏，或替换主内容区域并在顶部提供返回导航。

## 三、先确定核心对象和任务，再决定布局

设计前先明确：

1. 用户正在处理什么对象？
2. 用户最常做的事情是什么？
3. 当前状态是什么？
4. 用户下一步最需要执行什么操作？

围绕这些内容组织页面：

- 核心对象和高频操作应尽早出现在首屏。
- 列表、图片、编辑内容等实际工作区域应占据主要空间。
- 关键状态、必要字段直接展示。
- 说明文字、低频设置、原始资料、诊断信息按需展开。
- 删除重复标题、重复说明和没有实际作用的容器。

优先使用留白、对齐和分隔线区分区域，确有必要时再使用面板。避免大框套小框、卡片套卡片，也不要为了填满页面添加统计卡片或无关功能。

## 四、全局操作的位置是硬性约束

**作用于整个页面、完整表单、整个业务对象或全页数据的操作，统一放在页面头部右上角，并在滚动时保持可见。**

例如：保存整个对象、提交整个表单、发布、全局应用，以及作用于全页全部数据的操作。

必须遵守：

- 全局“保存”不得放在子模块内部。
- 全局操作不得放在内容末尾，不能要求用户滚到底部才能操作。
- 不在多个子模块重复放置实际作用于整页的保存按钮。
- 页面头部左侧安排返回、标题和必要状态；右侧安排全局操作。
- 右上角突出最重要的主操作，其余全局操作使用次要按钮或更多菜单。

**根据实际作用范围判断全局或局部，不能只看按钮名称。**

模块内部、行内或底部上下文操作条，只放明确作用于当前模块、当前记录或当前选中项的局部操作，例如“应用到选中 3 项”“重试此项”“添加一行”。

如果同时存在“局部应用”和“全局保存”，必须说明两者关系，让用户清楚局部操作是否已经持久化。

## 五、局部操作与批量操作

操作应尽量靠近其作用对象，减少用户在页面上下反复移动。

- 高频局部操作直接展示。
- 低频操作收进更多菜单。
- 长列表根据需要使用固定工具栏、固定表头或上下文操作条。
- 只有出现选中项时，才展示针对选中项的批量操作区域。
- 固定操作区域必须预留空间，不得遮挡内容。

必须明确区分：

- 当前查看的对象；
- 本次勾选的对象；
- 对象是否启用。

查看状态可以用行高亮表达，批量选择用复选框，启用状态优先用开关。点击查看详情，不应自动改变批量勾选或启用状态。

批量操作必须明确作用范围和数量：

- 已选 N 项；
- 当前筛选结果 N 项；
- 全部 N 项。

不要用含糊的“应用”“全选”同时代表不同范围，也不能把当前屏幕渲染出来的几行当作全部数据。
## 六、禁止弹出窗体，统一使用页内展示

### 1. 禁止使用弹出窗体承载业务流程

详情、编辑、新建、设置、批量处理和确认流程，不得使用 Dialog、Modal、Popup 窗体或带遮罩的悬浮抽屉。

业务内容只允许采用以下两种展示方式：

**方式一：在页面右侧展开详情。**

- 左侧保留原列表或主要工作区域。
- 右侧使用嵌入页面布局的详情分栏，不能用浮层覆盖主内容。
- 点击不同对象时，右侧切换为对应对象的内容。
- 右侧详情顶部提供明确的返回或收起入口。
- 收起后恢复主区域空间，并保留原有列表状态。
- 详情位置固定为右侧，不自行改成左侧。

**方式二：替换当前页面的主内容区域。**

- 保留应用外框和全局导航。
- 在当前主内容区展示完整详情或编辑页面。
- 顶部左侧必须提供“← 返回列表”或“← 返回上级”等明确导航。
- 返回后恢复此前的搜索、筛选、排序、勾选、滚动位置及相关设置。
- 不通过弹出新窗体承载完整详情或编辑流程。

### 2. 按任务复杂度选择展示方式

需要持续浏览列表、快速查看或处理单项内容时，使用右侧详情分栏。

内容较多、编辑时间较长、需要较大工作空间时，替换主内容区，并提供顶部返回导航。

### 3. 全局操作始终位于页面右上角

无论采用哪种展示方式，作用于整页或完整业务对象的保存、提交等全局操作，都必须固定在页面主头部右上角，滚动时保持可见。

不得把全局保存放入右侧详情的内部子模块、局部卡片或内容末尾。

### 4. 确认与未保存提醒也采用页内方式

需要二次确认或处理未保存修改时，使用页内确认条、行内确认区或当前内容区中的确认状态，不使用模态弹窗。

需要离开时，可在页内提供“保存并返回 / 放弃修改并返回 / 继续编辑”。保存失败则留在当前编辑区域，并保留输入内容。

以上为硬性约束。其他条款中允许业务弹窗、悬浮详情或自行选择详情左右位置的表述，应统一删除或按本节修正。

## 七、表单、列表与内容展示

### 表单

- 按业务关系分组，不按字段数量机械均分。
- 长文本分配足够宽度，短字段保持紧凑。
- 单位、字段含义和数据来源表达清楚。
- 只读信息不必全部做成输入框。
- 保留必要标签，不能只依靠占位文字说明字段。
- 校验信息出现在相关字段附近。

### 列表和表格

- 使用清晰的表头、对齐和细分隔线。
- 金额、数量等数据保持一致的格式与对齐。
- 长标题、URL 可以视觉省略，但应提供完整查看或复制入口。
- 面向连续编辑和批量操作的列表优先考虑连续滚动。
- 是否分页、虚拟滚动，应根据任务规模和实际能力决定；用户明确要求不分页时必须遵守。

### 图片和卡片

- 让主体内容占据主要面积。
- 仅保留必要名称、尺寸、状态和关系标签。
- 避免每张卡片堆叠多个大按钮。
- 预览、批量选择、用途或关联设置应有不同的入口和反馈。

## 八、状态、反馈和保存语义

每个对象应让用户看清：

- 当前是什么状态；
- 是否需要处理；
- 下一步可以做什么。

区分未开始、进行中、等待处理、成功、失败等状态，不能只靠颜色表达。

- 计数、进度和错误信息必须有真实依据。
- 未知信息显示“未提供”“未返回”或相应空状态，不编造数值和失败原因。
- 执行结束与执行成功应分别表达。
- 禁用操作应能让用户理解原因。
- 成功反馈简短，失败反馈说明问题并提供可执行的下一步。
- 可恢复的操作优先提供撤销，不为每次普通编辑增加确认弹窗。

明确区分即时生效、局部应用和等待全局保存的修改。

离开编辑页时，只针对实际未保存的内容处理。需要提示时，可提供“保存并离开 / 放弃修改 / 继续编辑”；保存失败保留当前内容。

已经保存的数据、上传结果或后台处理结果，不应因为放弃其他未保存编辑而被意外删除。

## 九、所有状态和结果必须归属正确对象

列表中的对象、当前查看对象、批量选中对象和正在执行的对象，应分别管理。

- 切换查看对象时，其详情、结果和诊断必须同步切换。
- 异步返回只能更新其所属对象。
- 后台处理下一项时，不要自动打断用户正在查看的内容。
- 本次执行与历史执行结果必须明确区分。
- 重试失败时，已有成功结果应按实际业务规则保留并标为历史，不能冒充本次结果。

## 十、设计边界与输出要求

- 依据实际业务、真实字段和现有能力设计。
- 可以重新组织信息、调整操作位置、合并重复入口和简化流程。
- 如果需要改变业务行为，应明确说明变化及影响。
- 不凭设计想象新增接口能力、自动化能力、业务指标或后台处理机制。
- 效果图使用示例数据时，应明确其示例性质。
- 如果涉及实现，优先沿用项目已有组件、主题变量和交互约定。

开始设计时，先用少量要点说明核心对象、主要任务和布局选择，然后直接给出可评审的设计成果。

交付前检查：

1. 核心对象和主要操作是否容易找到？
2. 全局保存、提交等操作是否固定在页面右上角？
3. 局部与批量操作的作用范围是否清楚？
4. 是否存在重复标题、无效留白和多层套框？
5. 返回、切换、保存和异步处理是否保持正确状态？
6. 是否始终保持统一的深灰＋绿色视觉风格？
