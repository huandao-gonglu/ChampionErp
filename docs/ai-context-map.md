# Backend AI Context Map

This map exists to reduce context scanning for humans and coding agents.

## Start Here

- HTTP protocol wrapper: `erp_web/http_handler.py`
- HTTP route dispatch table: `erp_web/http_routes.py`
- HTTP route units: `erp_web/http_route_units/`
- Route-facing business facades: `erp_web/facades/`
- Runtime namespace aggregator: `erp_web/runtime.py`
- Database access: `erp_web/db.py` (`ErpDatabase` class; schema v3 via `PRAGMA user_version`, version mismatch drops and rebuilds all known tables). Business code reaches it through `get_context().db` (`erp_web/context.py`). Tables: `products`, `platform_drafts`, `media_assets`, `store_auth`, `publish_logs`, `upc_pool`, `order_notifications`, `publish_jobs`.
- Product model API: `erp_web/product_model/`
- Marketplace publishing API: `erp_web/marketplaces/`
- Service modules: `erp_web/services/`
- Core shape hints: `erp_web/schemas/`

## Route Areas

- GET pages, state, static files, status APIs: `erp_web/http_route_units/get_routes.py`. `/api/state` declares `schemaVersion: 1` and is checked at runtime by `erp_web/schemas/api.py`; product payloads declare `schema_version: 1`. State/settings responses pass app/store config through recursive public redaction, so cookies, API keys, tokens, secrets, PKCE verifiers, and nested provider credentials never leave the backend in plaintext.
- Collection and browser collection APIs: `erp_web/http_route_units/collect_routes.py`
- Copy and prompt generation APIs: `erp_web/http_route_units/copy_routes.py`
- Auth, AI config, and settings APIs: `erp_web/http_route_units/auth_config_routes.py`. Store credentials and dynamic auth state (tokens, app secrets, code_verifier, user ids, auth_status, ...) live only in the `store_auth` table; `config/store_config.json` keeps non-sensitive static fields (site_id, listing defaults). `product_store.load_store_config()` composes both; `save_store_config()` splits writes.
- AI Work read-only conversation APIs: `erp_web/http_route_units/ai_work_routes.py`; each Provider call appends one isolated JSONL under `data/logs/ai_work/YYYY-MM-DD/{conversation_id}.jsonl`. The hidden Vue route `/aiWork` is implemented by `front/src/views/AiWorkView.vue` and reads one selected conversation incrementally.
- Global AI function prompts are JSON-backed through `erp_web/services/ai_prompt_templates.py` and saved in `ai_use_case_prompts`; each row points to one file with `description`, `system`, and `user`. `research.web_search` is the default AI product-research template and is edited from the global function-binding settings.
- Category live search, attributes, suggestion, and precheck APIs: `erp_web/http_route_units/category_routes.py`
- Product save/load/delete, independent platform draft detail/save, pricing, and UPC-pool import (`POST /api/upc-pool/import`) APIs: `erp_web/http_route_units/product_routes.py`
- Product research temporary hot-product runs (`POST /api/v1/product-research/hot-products/search`) create async runs; `GET /api/v1/product-research/hot-products/runs?run_id=...` polls status, source results, and weak progress descriptions. Source registry/settings APIs and search provider test API live in `erp_web/http_route_units/product_research_routes.py`, backed by `erp_web/facades/product_research_facade.py` and `erp_web/services/product_research_service.py`.
- Product research defaults and config normalization: `erp_web/product_research_config.py`; default prompt loading and template rendering use `erp_web/services/ai_prompt_templates.py`; user-facing search methods live in `product_research.search_providers`. Target markets (`product_research.target_markets[]`) own their search-method bindings in `search_methods[]`, while each concrete search method implements the `ProductResearchSearchMethod.run(...) -> list[HotProductCandidate]` contract in `erp_web/services/product_research_methods.py`. Hot-product candidates are runtime results from the selected search methods and are not stored in product-research settings.
- Product research AI search prompts are decoupled from search providers. The default template is `ai_use_case_prompts.research.web_search.path` such as `config/prompts/ai_example.json`; target-market generated prompts are stored per binding in `product_research.target_markets[].search_methods[].prompt` and are not shown in global function binding.
- Product research AI web search is a first-class search provider strategy (`source_type: ai_search`, `config_json.provider_strategy: ai_web_search`). It exclusively resolves its model through the global `research.web_search` function binding in `erp_web/services/ai_gateway.py`, and streams model output tokens into the async run `description` while the run is still active.
- Product research run summaries append to `data/logs/product_research_runs.jsonl` from `erp_web/services/product_research_service.py`; records include run id, target markets, source status, item count, and candidate previews. Temporary run snapshots are cached under `data/cache/product_research/runs/{run_id}.json` with `expires_at`; these cached `HotProductCandidate` rows support refresh/debug recovery and are not formal product records.
- Publish precheck, payload preview, real publish, and queue APIs: `erp_web/http_route_units/publish_routes.py`
- Logistics and fulfillment APIs: `erp_web/http_route_units/logistics_routes.py`; YunExpress/云途 client, OAuth token, HmacSHA256 signing, shipment preview, and `POST /api/logistics/yunexpress/create-shipment` live behind `erp_web/facades/logistics_facade.py` and `erp_web/runtime_units/yunexpress_client.py`.
- Mercado Libre order notification webhook: `erp_web/http_route_units/mercadolibre_routes.py` handles `POST /api/mercadolibre/notifications`; recent order pull and notification cache are exposed from `GET /api/mercadolibre/orders` in `get_routes.py`.
- Each route unit declares `HANDLED_PATHS` and a handler map (`GET_HANDLERS` or `POST_HANDLERS`) so a path can be resolved without reading the whole route file.
- Product, product research, collection, and publish routes delegate orchestration to `erp_web/facades/product_facade.py`, `erp_web/facades/product_research_facade.py`, `erp_web/facades/collect_facade.py`, and `erp_web/facades/publish_facade.py`.
- Runtime unit modules under `erp_web/runtime_units/` use explicit imports. `runtime_common.py` only holds shared constants and legacy common dependencies; do not use it as a wildcard dependency source.
- Publish and collection compatibility aggregators (`publish_runtime.py`, `source_collect.py`) use explicit export lists instead of wildcard imports.
- Static assets and auth helper pages: `erp_web/http_route_units/static_routes.py`
- Image upload and image pool API: `erp_web/http_route_units/image_routes.py`; image translation and image-to-image editing are orchestrated by `erp_web/services/image_translate_service.py`, while all production image model calls flow through `erp_web/services/ai_gateway.py` and `erp_web/services/ai_image_provider.py`.
- Product collection workflows: `erp_web/runtime_units/source_collect_workflows.py`. Source detection, parser selection, login/captcha/region diagnosis, browser profile, error-code mapping, and quality gates are descriptor-driven through the 1688/Amazon/generic registry in `erp_web/runtime_units/source_sites.py`.
- Product persistence and index: `erp_web/runtime_units/product_store.py`. Product profile saves intentionally strip `drafts`; platform draft text/detail editing uses `load_draft_detail_from_index()` and `save_draft_detail()` so one `draft_id` updates one `platform_drafts` row. Draft IDs are opaque (`"d" + uuid4().hex[:12]`); the platform of a draft is only the `platform_drafts.platform` column, never encoded in the ID.
- Image pool pure helpers and display/read logic: `erp_web/runtime_units/image_pool_core.py`
- Image pool persistence and product mutation actions: `erp_web/runtime_units/image_pool.py`
- Draft image references are structured asset refs (`asset_id`, `role`, `order`) normalized by `erp_web/product_model/draft_image_model.py`; image files and metadata stay in product `source.image_pool`.
- Copy generation: `erp_web/runtime_units/copy_generation.py`. Generated copy is saved through `save_draft_copy_result()` into one platform draft row and `/api/generate-copy` returns `draft`/`productContext` for independent draft editing.
- Live category lookup and attribute schemas: `erp_web/runtime_units/category_store.py`, `erp_web/runtime_units/category_providers.py`, `erp_web/runtime_units/category_refresh.py`, `erp_web/runtime_units/ozon_category_api.py`. Common category orchestration depends on the `CategoryProvider` contract in `erp_web/marketplaces/category_provider.py`; Mercado Libre and Ozon own their provider implementations. Ozon's category tree uses a locked TTL cache. Both searches do not read or write local category data stores.
- Publish precheck and payloads: `erp_web/runtime_units/draft_publish_context.py`, `erp_web/runtime_units/publish_validation.py`, `erp_web/runtime_units/publish_helpers.py`. `draft_publish_context.py` is the draft-first target resolver for `draft_id + platform + site`; it rejects targets outside the draft `target_sites`, builds the temporary product view used by validation/payload generation, and writes category/precheck results back to the selected `target_sites[]` item. Target-site listing data such as `category_id`, `category_path`, `category_attribute_schema`, `attributes`, `validation_errors`, and `publish_status` belongs to the selected target item; `category_attribute_schema` stores the normalized platform field definitions while `attributes` stores the draft's entered values. Root draft fields are only UI edit mirrors for the currently selected target.
- Platform capabilities and descriptors: `erp_web/marketplace_registry.py`. Only capabilities declared here may be exposed by common flows. Publish orchestration resolves a real `PlatformPublisher` through `erp_web/runtime_units/publish_adapter.py`; Mercado Libre is the only registered publisher, while Yandex/Ozon return `supported: false` instead of simulated success.
- Mercado Libre publish flow: `erp_web/runtime_units/publish_mercadolibre.py`
- Mercado Libre order notifications and recent orders: `erp_web/runtime_units/mercadolibre_orders.py`; webhook payloads insert into the `order_notifications` table and reads query it (id desc).
- Publish queue: `erp_web/runtime_units/publishing_bus_core.py`, `erp_web/runtime_units/publish_bus.py`. Job state persists in the `publish_jobs` table (no credentials/config inside; platform config is fetched from store_auth at execution time); the bus rejects missing required category attributes before invoking a publisher. Publish logs insert into the `publish_logs` table with artifacts still written as files under `data/logs/publish_artifacts/`.
- Product model units: `erp_web/product_model/` use explicit imports and export the public model API from `erp_web/product_model/__init__.py`.
- Marketplace publish units: `erp_web/marketplaces/` use explicit imports and export the public marketplace API from `erp_web/marketplaces/__init__.py`.
- AI gateway stable API: `erp_web/services/ai_gateway.py` is a small compatibility facade. Response/SSE parsing lives in `ai_gateway_parsing.py`; the single capability-probe loop and probe context live in `ai_gateway_probe.py`; API/CLI/browser Provider implementations and `AiProviderClient` live in `ai_gateway_providers.py`. Public `chat_json`/image/model-test signatures remain on the facade.
- AI model config and unified gateway: `erp_web/services/ai_model_config.py`, `erp_web/services/ai_gateway.py`, `erp_web/services/ai_provider_contracts.py`, `erp_web/services/config_service.py`, `erp_web/app_config.py`. Category translation/fill/identification and other prompt-backed JSON business functions enter through `erp_web/runtime_units/ai_use_case.py`, which centrally loads the binding/template, renders `input_json`, calls the gateway, and applies a use-case normalizer. `AI_USE_CASES` is the single capability contract for business functions: model rows declare the upper bound of supported capabilities, function binding only selects an eligible model and may set `timeout_override_seconds`, and runtime requests activate only the selected function's `required_capabilities`. Provider-specific activation parameters belong to the model row's `capability_profiles`; a successful capability probe returns the exact tested recipe and the UI saves it under that capability. Chat/Responses production requests compose their capability fields from those saved recipes, so use cases never hardcode Provider parameters. Old model configs without profiles retain a protocol-specific compatibility fallback. A model supporting `web_search` must not make ordinary copy/category calls search the web; only a function contract containing `web_search` may add the tested Provider search body. The default `json` compatibility recipe maps to `response_format: {"type":"json_object"}` for Chat Completions and `text: {"format":{"type":"json_object"}}` for Responses. Text calls stream internally by default so AI Work receives token deltas, while callers still receive the final parsed JSON object; an explicit `stream=False` remains available for Provider fallback paths. Binding timeout overrides the model timeout. `AiProvider` owns only capability resolution; `AiChatProvider` and `AiImageProvider` expose focused text and image interfaces. OpenAI-compatible image generation/editing lives in `erp_web/services/ai_image_provider.py`; business modules must not import model SDKs directly. Model rows use `connection_type` to choose `api`, `cli`, or `browser`; API rows keep an explicit `api_style` (`openai_compatible` / `openai_responses`), optional legacy `extra.web_search_request_mode` (`enable_search` or `web_search_options`) / `extra.web_search_request_body`, and optional `extra.request_body`. `extra.request_body` is a user-entered model-wide JSON object shallow-merged into each Chat/Responses request after the standard and capability bodies have been built, including capability probes; transport-controlled `stream` is restored after merging. Responses API web search defaults to `tools: [{"type":"web_search"}]`; Chat Completions probes the configured provider extension first, then its other built-in extension candidates, with `enable_search` additionally sending `search_options.forced_search: true` unless overridden. Capability probes never change the configured API style or cross from Chat to Responses (or conversely). Capability selection is transactional: opening a probe snapshots the selected capabilities, and a failed, cancelled, or incomplete probe restores that snapshot; only a successful probe saves its profile and adds the tested capability. Changing connection-dependent model fields or unchecking a capability clears the stale profile. CLI rows keep `cli_tool`, `command`, optional `profile`, `sandbox`, and execute through the Codex CLI adapter with separate probes for text/JSON, live web-search evidence, and image-generation output references, while browser rows keep `browser_provider`, `browser_mode`, optional `browser_profile`, `browser_port`, and `browser_url`. Browser AI sessions run through `erp_web/services/browser_ai_runtime.py`, using Chrome remote debugging with managed profiles under `browser_profile/ai/<provider>/<profile>/` by default; users log in manually in the opened browser window. Do not persist or consult derived negative fields such as `unsupported_capabilities`, `detected_capabilities`, or `effective_capabilities`. Every production Provider invocation creates an AG-UI-compatible conversation journal through `erp_web/services/ai_work_service.py`; `RUN_STARTED.rawEvent` records effective capabilities, stream mode, and timeout, actual Provider requests use `CUSTOM/provider.request`, streamed text uses `TEXT_MESSAGE_*`, and parsed business output uses `CUSTOM/business.result`.

## Data Shapes

- Product and source fields: `erp_web/schemas/product.py`
- Image pool items and draft image refs: `erp_web/schemas/image.py`
- Publish jobs: `erp_web/schemas/publish.py`
- App/store config: `erp_web/schemas/config.py`
- Product research search providers, target markets, temporary hot-product candidates, and run results: `erp_web/schemas/product_research.py`
- AI Work event and conversation summary shapes: `erp_web/schemas/ai_work.py`
- API response envelope and runtime `/api/state` contract validator: `erp_web/schemas/api.py`

## Frontend Entry Points

- The workflow UI has one real route, `/`, implemented by `front/src/views/workflow/WorkflowView.vue`. Its sections use the canonical `?tab=<key>` query. Historical paths such as `/collect`, `/pricing`, and `/publish` are compatibility redirects in `front/src/router/index.ts`; they must not mount duplicate copies of the workflow component.
- `front/src/stores/workflow.ts` is the compatibility-facing workflow orchestrator. State ownership and focused actions live in `front/src/stores/workflow/activity.ts`, `catalog.ts`, `collection.ts`, `publishing.ts`, and `settings.ts`. Add new state to its owning domain store instead of adding another unrelated ref to the orchestrator.
- This is a local single-user application. `front/src/api/client.ts` adds locale/timezone request context but does not invent an application-user Bearer token. Marketplace OAuth credentials remain backend-managed store credentials.
- `front/src/api/workflow/normalizers.ts` is the product contract boundary. Unversioned products may use legacy aliases for migration, but `schema_version: 1` reads canonical fields and `toBackendProduct()` writes only the version-1 projection.

## Compatibility Notes

- `erp_web/runtime.py` provides the runtime namespace used by the current HTTP app. Prefer reading the unit module named in this map instead of starting from the runtime namespace.
- `erp_web/http_handler.py` should stay thin. New API behavior should go into a focused route unit or service module, not directly into the handler class.
- Route units should use explicit imports or focused facades. Do not add new `from erp_web.runtime import *` imports; `erp_web/runtime.py` is only a runtime namespace aggregator.
- `erp_web/runtime_units/image_pool_core.py` is the dependency-light layer for image refs, dimensions, and pool display helpers. Product storage and publish modules should depend on it instead of importing `image_pool.py`.
- `tests/test_ai_context_architecture.py` locks the no-wildcard rule for route/facade layers, product/marketplace units, and runtime unit modules.
