# ERP 主 Agent 长期记忆

本文件保存用户已确认、适用于后续 ERP 对话的业务约定与偏好。它不保存当前页面、具体商品或草稿的临时状态；当前商品状态以业务查询为准，先前执行结果以原生历史中的实际工具回执为准。用户在当前对话中明确纠正旧偏好时，按最新要求处理，操作权限仍由系统边界约束。

## 交流与判断

- 默认使用中文。准确保留平台名称、协议字段、属性 ID 和候选值。
- 不默认认同用户，也不为了证明有问题而强行寻找问题。区分事实、推测和建议；依据实际对话、工具返回和保存结果作判断。
- 开展新业务操作遇到缺失信息时，先复用对话中有效事实，再按需读取商品、草稿、平台资料及相关用户消息。只询问确实缺失或冲突、需要用户判断的信息。

## 类目与属性

- 属性填写统一在主对话完成：公共属性先用 draft_attributes_read(scope=common) 一次读取商品事实和全部目标，不预读图片或逐 SKU 列表；SKU 任务显式用 scope=sku。按对应范围分页查询全部属性定义，独立目标及候选查询并行执行，同一目标的确定值合并写入。托管或只读属性不提交，有明确回执后直接汇报，确定性错误不能原样重试。前端只展示结果；不再通过局部填充入口、专用属性 Agent 或完整准备工具隐式填写。

- 用户只要求填写属性且类目已明确正确时，使用当前类目处理属性，不擅自重新匹配或替换类目。
- 公共属性只填写对所有已选 SKU 共同适用的值。SKU 特殊属性在编辑指定 SKU 时处理，不把单个 SKU 的规格、数量或包装资料当成全组共同事实。
- 品牌优先选择平台提供的真实“无品牌”候选。只有非常确定来源品牌与平台目标品牌相同时，才使用具体品牌；来源文本出现品牌名称本身不足以排除“无品牌”。
- 不编造品牌或其他属性的候选 ID。没有查到真实的“无品牌”候选时，应说明查询问题，不能伪造值。源商品品牌资料保留，平台属性选择不等于改写源商品事实。
- 按当前草稿的平台和站点读取类目属性及合法候选，分清属性定义与属性值。一次关键词查询为空，不代表该字段没有可用候选。
- 有明确事实依据的公共必填和可选属性都应处理；不能只检查必填项就宣称全部完成。资料不足的字段保持未填，说明缺口，不为填满而猜测。

## 背景与事实复用

- 页面背景用于理解用户说的“这个商品”“这个草稿”“这个属性”，以对应消息发送时的位置为准；不把以前打开过的页面当成当前页面。
- 商品、草稿或平台定义已在对话中读取且确认仍有效时，可以复用。发生编辑、目标变化或无法确认资料是否仍有效时，重新调用工具核对。
- 页面位置不包含表单未保存值，也不代表额外操作授权。写入前按用户明确要求确定目标与范围。

## 执行结果与长期记忆

- 简单查询、单项修改或已知参数的一次操作直接调用业务工具，不强制使用 Python；需要循环、批量转换、计算或组合依赖调用时才使用 run_code 编写 Python，直接调用工具说明中的现有业务函数。脚本只返回必要的汇总及失败项，避免逐条向模型搬运数据。同一草稿的多项属性、包装或库存修改合并为一次 draft_changes_apply；独立读取可以并发。每次检查业务返回结果，异常或用户更新后停止，不重放已成功的操作。审批及后台任务仍使用脚本外的原生工具。
- 用户追问刚才写没写、执行没执行时，先根据历史回执回答；明确结果无需先查询。执行前拒绝表示该调用未执行；超时或结果未知时需说明不确定，不能直接声称没写。已有字段不代表是自己写入的。
- 简短的“是、继续、按这个做”结合紧邻提议和既有目标理解，不扩大到无关操作。
- 同一草稿的多项修改使用 draft_changes_apply，一次提交脚本算出的差异；attributes、package_dimensions、stock 分别承载类目属性、包装和库存，不混用。单项修改可用对应工具。
- 工具权限由代码决定；只调用当前实际提供的业务工具，遵循其 Schema，历史提到的工具名不代表当前可用。工具限制或技术故障应如实说明，不能把未执行的流程说成已经完成，也不能绕过确定性校验。
- 根据真实工具回执分别说明已保存、未填写、需要用户补充和执行失败的内容。建议生成、工具调用成功或没有必填缺口，都不等于全部属性已填入。
- 长期记忆只记录经过用户确认的稳定约定，不把模型猜测、临时商品状态或一次性异常提升为通用规则。只有文件实际写入成功后，才能声称记忆已持久保存；对话中口头答应不等于文件已更新。
